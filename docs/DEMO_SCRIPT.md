# KeyGuard 2.0｜5 分钟演示脚本

这是一份求职 Demo 讲稿，不是业务上线材料。演示全程遵守以下口径：**不得声称真实客户、不得声称真实资产、不得声称企业降本、不得声称生产 SLA、不得预填 V2 评测数字**。V2 指标只能在真实 runner 完成后现场读取。

演示前准备：

- 本地执行 `pytest -q`，确认测试通过。
- 打开“客户对话”和“工单工作台”两个标签页。
- 配置 `KEYGUARD_OPERATOR_TOKEN`，并保留一个未授权窗口用于展示默认关闭。
- 清理或新建演示工单，准备 Bluetooth、固件、测试助记词、`A1B2` 四个案例。
- 不使用任何真实助记词、私钥、账户、序列号或客户信息。

## 0:00–0:40｜从 V1 审计到 V2 风险边界

**讲解**

“V1 能完成 RAG 问答，但业务状态隐含在 ReAct 消息里，职责、返工和人工接管不够清楚。V2 把一张工单拆给 Triage、Diagnosis、Review 三个 Agent；路由、状态迁移、安全门和人工动作由确定性代码控制。”

**操作**

1. 快速展示 README 的 V1 → V2 表格和七状态图。
2. 切到应用，指出“客户对话”与“工单工作台”。
3. 在未授权窗口打开工作台，展示未配置或令牌错误时默认拒绝访问。

**观察点**

- Router 不是第四个 Agent。
- Ingress Guard 在持久化前脱敏，Policy Guard 在输出前校验。
- 高风险具有风险粘性，Review 最多一次返工，失败后交给人工。

## 0:40–2:00｜蓝牙自动解决：从分诊到证据引用

**讲解**

“先演示一条无需人工介入的 happy path。重点不是回答看起来像不像客服，而是每一步都有结构化状态和证据。”

**操作**

1. 在客户对话输入：“KeyGuard 蓝牙连不上手机，手机蓝牙权限已开，App 和系统都是最新版。”
2. 展示工单从 `new`、`triaged`、`diagnosing`、`reviewing` 到 `resolved`。
3. 展开事件和证据，指出 Diagnosis 调用了知识检索，回答中包含来源引用。
4. 若时间允许，快速新建固件案例：“固件升级中断了，现在怎么办？”先不提供设备型号和错误状态。

**观察点**

- Bluetooth 案例在信息充分时自动完成。
- 固件案例缺少必要字段时进入 `pending_user`，不会编造设备专属步骤；补充设备型号和错误状态后重新进入分诊。
- Agent 生成内容，Tool 返回知识事实，Router 决定下一跳。

## 2:00–3:40｜助记词脱敏、固定提示、升级人工与恢复

**讲解**

“第二条主路径故意触发安全边界。这里用测试词串，绝不能用真实秘密。随后用模拟保修案例展示另一种人工门禁。”

**操作**

1. 在客户对话粘贴仓库测试使用的助记词样例，并询问能否帮助恢复钱包。
2. 展示用户界面的固定安全提示：系统不会索要、保存或复述秘密。
3. 打开工作台，确认工单和审计事件中只有脱敏内容，且状态为 `escalated`；指出风险粘性阻止后续静默降级。
4. 用授权操作员执行“向用户追问”，让工单进入 `pending_user`；补充非敏感信息后展示 checkpoint 恢复。
5. 新建保修案例并只提供序列号后四位 `A1B2`。展示 Warranty Tool 返回的是模拟保修证据，涉及保修决定时仍停在人工门禁。
6. 展示“批准”“编辑后发送”“拒绝”动作，但只选择一个与当前案例一致的动作完成演示。

**观察点**

- 秘密在数据库和 checkpoint 之前被处理，而不只是最终回答里隐藏。
- 高风险内容不会被普通对话覆盖。
- Human-in-the-loop 是可恢复的业务状态，不是口头说“转人工”。
- `A1B2` 只用于模拟查询，不代表厂商真实保修系统。

## 3:40–4:30｜48 条案例、评测产物与 bad case

**讲解**

“V2 评测集有 48 条，即 30 条继承案例加 18 条编排专项案例。它评估路由、状态、脱敏、证据和人工接管。仓库里的 V1 结果是关键词覆盖率，不能当作 V2 准确率。”

**操作**

1. 打开 `eval/multi_agent_cases.json`，展示场景覆盖而不是逐条朗读。
2. 若已连接真实 runner，现场运行评测并打开结果 JSON：先看 aggregate metrics，再看逐 case 的 `scores`、`status_trace` 和 `citations`；**不得预填 V2** 数值。
3. 从未通过的 `scores` 选择一个 bad case，按“预期状态—实际状态—哪条边界失败—如何增加测试或修正路由”复盘。
4. 若 runner 未配置，明确展示 stderr 中的配置错误；此时不会生成评测结果文件，是零结果产物，不能临时制作结果。

**观察点**

- 指标来自当次可复现执行，而非 README 手填。
- aggregate metrics 用于总览，逐 case 结果与 bad case 用于定位路由或安全边界问题。
- V1 的 83.3% 只表示 30 题关键词覆盖率。

## 4:30–5:00｜为什么是 3 个 Agent，以及为什么 Router / Tool 要确定性

**收尾讲解**

“三个 Agent 分别处理判断问题、查证问题和审查问题，使职责与失败边界可单测。Router 不需要语言创造力，所以使用确定性规则；Tool 返回数据库或知识库事实，也保持窄接口。这样模型负责擅长的理解与生成，代码负责状态、安全和副作用。”

最后补充三条边界：

1. 这是使用模拟数据的工程 Demo，不处理真实资产。
2. SQLite 与 Streamlit Cloud 本地文件系统不能替代生产持久化。
3. 下一步生产化方向是外部数据库、企业身份权限、真实工具适配、在线监控和经真实 runner 复现的评测基线。
