# KeyGuard 客户进度与工单工作台设计规格

**日期：** 2026-07-30
**状态：** 待用户审查
**范围：** C + A 双层交互、普通 USB 工单返工稳定性、操作员工作台启用

## 1. 背景与问题

当前客户页面只在整个 V2 编排完成后才把用户消息和助手消息写入
`st.session_state["messages"]`。模型调用期间页面没有可见反馈；如果编排失败，
用户只看到最终的安全转人工文案，容易误以为输入消失。

本次观察到的 USB 连接工单实际经历了：

1. 入口安全检查完成。
2. 分诊完成，分类为 `usb_connection`。
3. 诊断取证完成，加载了知识库和用户档案证据。
4. Review 要求一次受限返工。
5. 二次 Diagnosis 结构化输出校验失败，工作流按 fail-closed 规则转人工。

因此本次改动同时解决两类问题：

- 普通低风险故障经过 Review 返工后仍应尽量稳定形成安全答复。
- 用户和操作员能看到安全的业务阶段与失败原因，而不是隐藏在一次提交后的空白等待中。

## 2. 目标与非目标

### 2.1 目标

- 客户提交后立即保留已经脱敏的用户消息，并显示处理中状态。
- 客户页显示简洁的安全进度：入口检查、分诊、取证、复核、回复。
- 工单工作台显示详细但安全的事件轨迹、证据摘要、Review 结果和人工动作。
- 保持现有 `ticket_events` 和 checkpoint 作为事实来源，不新增重复的工作流状态库。
- 修复 Review 要求返工时的 Diagnosis 结构化协议，使 USB/连接类低风险问题可稳定完成。
- 工作台通过独立操作员令牌启用；未配置令牌时继续 fail-closed。
- 不展示模型隐藏推理、Prompt、原始模型输出或敏感信息。

### 2.2 非目标

- 不实现 token-by-token 的模型流式输出。
- 不展示 chain-of-thought、推理草稿或内部 Prompt。
- 不引入企业级账号、角色权限、令牌轮换或审计平台。
- 不把模拟保修、链状态数据改造成真实外部交易或售后系统。
- 不通过静默删除字段、强制改写模型结果来绕过结构化校验。

## 3. 方案与最终选择

### 3.1 客户进度方案

比较过三种方案：

- **静态加载动画：** 改动最小，但无法解释编排阶段。
- **完整实时图流：** 阶段最真实，但需要重构 Runtime/Graph 的执行接口，风险和范围都较大。
- **混合方案（采用）：** 请求执行期间显示安全的阶段性处理中状态；执行完成后从已经持久化的
  `ticket_events` 回放真实事件。它保留当前同步 Runtime 边界，同时解决“无反馈”和“结果不可解释”。

### 3.2 访问层级

采用双层交互：

- 客户页：只显示普通用户能理解的阶段和结果。
- 工作台：操作员登录后显示详细的可审计轨迹和人工动作。

## 4. 客户页面设计

### 4.1 提交时序

`_run_v2_prompt` 按以下顺序处理：

1. 通过 `prepare_user_input` 完成入口脱敏和安全校验。
2. 用稳定 `request_id` 在会话状态中写入一条脱敏用户消息；同一个 request 不得重复追加。
3. 写入一个仅用于 UI 的助手占位消息，例如“正在安全处理你的问题…”。
4. 在调用 `submit_prepared` 或 `resume_user_prepared` 期间显示 `st.status`。
5. 成功后，用 `_answer_with_citations(result)` 替换占位消息。
6. `pending_user`、`escalated`、异常或恢复失败时，也替换占位消息并保留工单号和安全文案。

原始、未脱敏输入不得进入持久化消息或错误提示。

### 4.2 客户可见阶段

状态组件只使用白名单阶段映射：

- `entry_checked`：安全检查完成
- `triage_completed`：问题分诊完成
- `diagnosis_completed`：诊断取证完成
- `review_completed`：安全复核完成
- `response_finalized`：安全回复已完成
- `escalated`：已转人工审核

执行期间显示当前阶段和下一步提示，不显示工具参数、模型字段、Review 原文或异常正文。
完成后沿用现有工单状态、优先级、风险和引用来源展示。

### 4.3 客户错误体验

- 请求进行中：用户消息不消失，显示可识别的处理中状态。
- `pending_user`：显示需要补充的信息类别，并保持当前工单 ID。
- `escalated`：显示“工单已进入人工审核”，并显示已完成的安全阶段。
- Runtime/网络/恢复异常：显示安全失败文案；若已创建工单，保留工单号。

## 5. 工单工作台设计

### 5.1 认证

- 本地从 `.env` 读取 `KEYGUARD_OPERATOR_TOKEN`。
- Streamlit 从 Secrets 读取同名配置。
- 令牌不写入代码、README、日志或 Git。
- 使用现有 HMAC 会话证明；输入错误时不泄露比较细节。
- 未配置令牌时，工作台显示“未启用”并清理操作员会话与冻结动作。

### 5.2 工单列表

工作台列出安全投影后的工单摘要：

- 工单 ID
- 状态、优先级、风险等级
- 分类
- 是否需要人工
- 创建/更新时间

不得直接把 `metadata_json`、`draft_prompt`、`tool_args`、`model_output` 等内部字段渲染到页面。

### 5.3 工单详情

详情页显示：

- 脱敏后的问题摘要
- 事件时间线：入口、分诊、取证、复核、返工、升级/结案
- 只读工具名称和证据数量
- 已验证来源链接
- Review 的结构化原因码、问题摘要和必要修改项
- 当前草稿（经过安全投影）
- 人工动作：`Approve`、`Edit & Send`、`Ask User`、`Reject`

人工动作继续使用现有 prepare/freeze/submit 流程，保持幂等、租约和状态转移校验。

## 6. Diagnosis 返工稳定性设计

Review 返回 `revise` 时，revision 节点只允许执行一次返工。返工输入必须包含经过白名单校验的：

- 当前 category、risk_level 和 missing_fields
- 现有 evidence 引用
- Review 的结构化 reason_codes、issues、required_changes

Diagnosis 的返工系统约束需明确：

- 已进入回答阶段表示必要字段齐全。
- 普通低风险 USB/连接类问题只能使用 `generic_troubleshooting`。
- `remaining_unknowns` 必须为空数组才能返回 `draft`。
- 返工不得增加配置之外的必要字段。
- 如果仍不能形成符合契约的安全结果，继续 fail-closed，并在工作台展示稳定错误码和返工轨迹。

不得将不符合 schema 的结果静默修正成“看起来可用”的结果。普通 USB 路径应通过结构化返工提示和回归测试稳定通过，而不是依靠后处理绕过验证。

## 7. 数据流与边界

```text
用户输入
  -> prepare_user_input / 脱敏
  -> 客户页写入脱敏消息 + UI 占位状态
  -> SupportOrchestrator
  -> LangGraph: entry -> triage -> diagnosis -> review -> finalize/escalate
  -> ticket_events / checkpoint 持久化
  -> 客户页安全阶段投影
  -> 操作员工作台详细事件投影
```

- `ticket_events` 是进度回放的事实来源。
- 客户页只读取与当前 `user_id` 绑定的工单。
- 工作台只在操作员认证成功后读取安全投影数据。
- 证据链接必须经过现有 trusted source policy 验证。
- 错误日志只记录稳定 error code、节点名、异常类型和工单 ID，不记录输入、Key 或模型正文。

## 8. 测试与验收标准

### 8.1 单元与契约测试

- 脱敏消息在请求完成前写入，失败时仍保留。
- 同一 request_id 在恢复/重跑时不重复追加消息。
- 客户阶段投影只允许白名单 event_type。
- 工作台投影不包含内部 Prompt、工具参数或原始模型输出。
- Review `revise` 到 Diagnosis 的 payload 只包含结构化安全字段。
- USB/连接类返工结果不能使用不匹配的 manual action_code。
- 未配置、错误和正确操作员令牌的认证行为分别符合预期。

### 8.2 集成回归

1. `硬件钱包开不了机怎么办？`：低风险、带引用、`resolved`。
2. USB 连接问题完整长句：分诊为 `usb_connection`，经过 Review 后稳定 `resolved` 或有明确人工原因。
3. 固件问题缺少设备型号：`pending_user`，补充后复用同一工单。
4. 助记词/远程控制风险：高风险 `escalated`，不索要秘密。
5. ETH pending：缺字段追问后调用只读 chain status。
6. 1005 用户：记忆压缩和用户隔离不回归。

### 8.3 浏览器验收

- 客户提交后能看到用户消息和处理中状态，而不是空白。
- 成功工单显示完整安全阶段和引用来源。
- 转人工工单显示工单号、转人工原因和已完成阶段。
- 操作员登录后能查看一张工单并完成一次安全的 `Edit & Send` 测试。
- 未配置令牌的环境继续显示工作台关闭提示。

## 9. 发布顺序

1. 先实现纯函数投影、消息占位和 Diagnosis 返工契约。
2. 运行全量测试、真实 DeepSeek 最小回归和本地浏览器验收。
3. 本地配置一个独立的 Demo 操作员令牌；令牌不提交 Git。
4. 在 Streamlit Secrets 配置同名令牌，重启后验证登录和人工动作。
5. 推送 `main`，等待自动部署，重新验证成功、pending_user 和 escalated 三条路径。

## 10. 验收结论

只有同时满足以下条件才算完成：

- 普通 USB 问题不再因一次 Review 返工结构化失败而无解释地转人工。
- 用户输入和处理中状态在请求期间可见，失败后也不会消失。
- 客户页和工作台的展示层级符合 C + A 设计。
- 工作台的人工操作经过独立令牌、幂等和状态校验。
- 安全边界、敏感信息保护、fail-closed 和既有全量测试不回归。
