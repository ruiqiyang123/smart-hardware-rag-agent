# KeyGuard 2.0 用户自主转人工与窄风险升级设计

日期：2026-08-02
状态：已获产品方向确认，待书面规格审阅

## 1. 背景与问题

当前客户会话要求累计三次有效 AI 回答后，用户才能主动申请人工。与此同时，Triage、Diagnosis 或 Review 节点的结构化输出失败会统一 fail closed 到 `escalated`。这产生了两个与求职 Demo 目标冲突的体验：

1. 用户对第一次回答不满意时仍不能自主选择人工；
2. 普通低风险问题可能因为模型字段组合不合法而被误转人工。

已观察到的代表性 bad case 是“设备丢了或坏了，资产还能恢复吗？”。该问题在第三轮调用中连续两次未通过 `TriageResult` 校验，最终以 `TRIAGE_FAILURE` 转人工。该行为不是“三次对话后自动升级”的产品规则，而是节点失败兜底；但对用户而言两者不可区分。

本设计将人工升级拆成两条互不混淆的路径：用户自主申请，以及极窄、可解释的资金安全事件自动升级。

## 2. 目标

- 用户在任意一轮 AI 回答后都能立即申请人工，不设交互次数门槛。
- 保留持久化前敏感信息检测与脱敏，原始秘密不得进入模型、工单库或 checkpoint。
- 自动升级只覆盖明确的资金安全事件，不因普通设备、恢复或交易故障关键词升级。
- 普通问题的模型结构输出失败时进入确定性澄清，而不是自动转人工。
- 保留确定性 Router、Pydantic Schema、审计事件和工作台的可解释性。
- 使用明确的正反例约束“设备丢失”和“资产丢失”等易混淆概念。

## 3. 非目标

- 不移除 Ingress Guard，也不允许原始助记词、私钥、PIN 或 Passphrase 持久化。
- 不建设真实人工客服排队、SLA、坐席分配或通知系统。
- 不接入真实链上资产、厂商保修或生产身份权限。
- 不让 DeepSeek 自由决定最终状态；模型仍只返回结构化业务判断。
- 不新增大而全的通用 Skill 框架。本次只提供 Triage 使用的窄领域策略规则。

## 4. 核心产品规则

### 4.1 用户自主转人工

客户页始终展示可用的“联系人工客服”入口。用户点击入口，或明确输入“转人工”“找真人客服”“人工客服”等意图时，系统绕过 Triage，直接执行受审计的客户转人工命令。

- 不再读取或校验 `ai_attempt_threshold`；
- 不再显示 `1/3`、`2/3`、`3/3` 等人工准入进度；
- 转人工原因固定为 `customer_requested_human`；
- 命令仍要求当前工单为 `pending_user`，并继续使用幂等键、租约和版本边界；
- 用户自主转人工不等于问题解决，工单状态进入 `escalated`。

### 4.2 敏感信息检测与脱敏

Ingress Guard 保持确定性执行，并发生在任何模型调用或持久化之前。检测到疑似助记词、私钥、WIF、PIN 或 Passphrase 时：

1. 将秘密替换为受约束的 `[REDACTED_*]` 占位符；
2. 原始文本不得进入安全历史、Ticket Store 或 LangGraph checkpoint；
3. 客户页显示固定安全提示；
4. 是否自动升级由“是否已经发生凭证泄露事件”决定，而不是由“是否提到敏感名词”决定。

知识咨询如“助记词忘了怎么办”“Passphrase 有什么作用”继续由 AI 回答。用户实际粘贴秘密时至少执行脱敏和固定提示；若语义明确表明秘密已提交给第三方、钓鱼页面或远程控制人员，则进入自动升级。

### 4.3 自动升级白名单

仅以下已确认或高度明确的资金安全事件自动进入 `escalated`：

| 事件 | 代表性表达 | 风险标记 |
|---|---|---|
| 未授权资产移动 | “发现一笔不是我发起的转账” | `asset_loss` |
| 明确资产被盗 | “钱已经被陌生地址转走了” | `asset_loss` |
| 凭证已经泄露 | “我把助记词发给了陌生人” | `secret_exposure` |
| 钓鱼或恶意授权 | “我在可疑网站输入了私钥” | `phishing` / `secret_exposure` |
| 地址或签名异常 | “设备地址和手机显示的不一致” | `address_mismatch` |
| 未发起的签名请求 | “设备突然让我确认陌生签名” | `suspicious_signature` |

这些标记继续服从 Schema 风险下限：critical 风险使用 `P0 + escalate`，high 风险使用 `P1 + escalate`。入口已检测到的风险具有粘性，模型不能把它降级。

现有 `unofficial_firmware`、`device_auth_failure` 和泛化的 `remote_control` 不再仅凭 flag 自动升级：询问第三方固件、设备认证失败或远程协助知识时，系统先给固定安全警告或普通诊断；只有上下文已经表明钓鱼、恶意授权、秘密泄露或未经授权资产移动时，才映射到上述自动升级白名单。`address_mismatch` 与 `suspicious_signature` 继续作为资金安全相关 high 风险升级条件。

### 4.4 不自动升级的普通问题

以下场景默认进入 AI 自助或澄清，不因关键词自动升级：

- 物理设备丢失、损坏或无法维修；
- 备份仍在时咨询如何恢复；
- 恢复后余额为零；
- Passphrase、派生路径、账户添加或同步问题；
- 交易 pending、失败、Gas 过低或网络拥堵；
- App 暂未显示余额；
- 开机、屏幕、按键、USB、蓝牙和固件问题；
- 保修知识咨询；
- 设备重置或 Bootloader 恢复的非执行性安全说明。

`device_loss_damage` 明确定义为物理设备丢失或损坏，不能仅因出现“丢失”一词添加 `asset_loss`。`asset_loss` 仅代表已经观察到或明确怀疑未经授权的资产移动。

原有 `device_reset`、`bootloader_recovery` 和 `warranty_decision` 不再作为自动转人工门禁。AI 只能提供准备事项、风险说明和非执行性指导，不得声称已经替用户重置设备、进入恢复模式或批准保修；需要真实业务操作时，页面提示用户可自主点击“联系人工客服”。

### 4.5 不确定时先澄清

当用户只说“钱不见了”“交易有问题”等无法区分显示故障与安全事件的表达时，系统不得直接升级。Triage 应进入 `ambiguous` 或安全澄清路径，并询问具体情况：

1. App 暂未显示余额；
2. 恢复钱包后余额为零；
3. 交易长时间未确认或失败；
4. 发现本人没有发起的转账；
5. 助记词或私钥可能已经泄露。

前三项继续 AI 诊断，后两项进入自动升级。

## 5. Triage 策略包

现有 `TriageResult` 字段集合保持为输出契约，不新增数据库字段；其风险 flag 严重度联动校验按本设计的自动升级白名单收窄。新增或扩充一份运行时 Triage 策略规则，由 Triage Prompt 显式加载，内容至少包括：

- 每个关键 category 与 risk flag 的精确定义；
- `device_loss_damage` 与 `asset_loss` 的边界；
- 普通交易故障与未授权资产移动的边界；
- 敏感知识咨询与凭证已经泄露的边界；
- 代表性正例、反例和最小对比案例；
- 信息不足时的澄清问题和选项；
- 禁止只依据“丢失”“余额”“失败”“恢复”等单个关键词升级。

该策略包是项目运行时提示上下文，不是 Codex 的 `SKILL.md`，也不由 DeepSeek 自动发现。项目代码必须显式加载它，并与现有 Schema 一同传给 Triage 模型。

## 6. 低风险结构失败回退

当前 `_fail_closed` 会把任意节点失败统一改为 `escalated`。本次仅收窄 Triage 的低风险结构失败行为：

1. Triage 仍按现有超时和一次重试策略执行；
2. 若两次都因结构或校验失败，检查入口风险与已持久化风险；
3. 若存在 high/critical 风险、关键 risk flag 或 `requires_human`，继续 fail closed 到 `escalated`；
4. 若入口为 low/medium 且没有风险标记，生成确定性澄清结果，状态进入 `pending_user`；
5. 澄清回复不得由失败的模型草稿产生，也不得复用上一轮分类、摘要或风险作为本轮结论；
6. 审计事件记录稳定原因码，例如 `TRIAGE_FALLBACK_CLARIFICATION`，但不保存模型原始输出或异常文本。

固定澄清文案表达为：系统暂时无法准确判断问题类型，请用户在设备故障、连接问题、钱包恢复、交易显示异常和未经授权资产转移之间选择。

Diagnosis、Tool、Review 与最终 Policy Guard 的失败边界本次保持不变，避免把范围扩展为全局容错重构。

## 7. 确定性路由顺序

每一轮用户输入按以下顺序处理：

1. Ingress Guard 检测和脱敏；
2. Resolution Intent 检查用户是否确认解决；
3. Handoff Intent 检查用户是否主动要求人工；
4. 若主动要求人工，直接执行 `customer_request_human`；
5. 否则进入 Triage；
6. Router 根据有效结构化字段决定澄清、诊断或自动升级；
7. 低风险 Triage 结构失败进入确定性澄清；
8. 高风险失败继续 fail closed。

用户自主转人工和用户确认解决均由确定性意图检测处理，不依赖 Triage 模型是否可用。

## 8. UI 与工作台

### 客户页

- 人工入口始终可用，不显示次数门槛；
- 删除 AI 自助进度；
- 用户主动转人工时显示“已按您的要求转交人工客服”；
- 自动风险升级时显示具体但不泄露秘密的安全原因；
- 低风险 Triage 回退显示澄清问题，不显示“自动分诊暂不可用，已转人工”；
- 旧一轮的 category、priority 和 risk 不得被误展示为本轮失败结果。

### 工单工作台

工作台继续使用 `manual_gate_reason` 区分：

- `customer_requested_human`：客户主动申请；
- `asset_loss`、`secret_exposure`、`phishing`、`address_mismatch`、`suspicious_signature`：资金安全事件；
- 其他现有系统失败原因保持兼容。

低风险 Triage 回退不进入人工队列，但其审计事件应可在工单轨迹中查看。

## 9. 配置与兼容性

- 删除 `customer_handoff.ai_attempt_threshold` 及其严格配置校验；
- 不新增可调次数门槛；
- 删除 `manual_gate_actions` 对 `device_reset`、`bootloader_recovery` 和 `warranty_decision` 的自动升级路由及对应配置校验；
- 现有工单数据库 Schema v8 不需要迁移；
- 现有 `customer_request_human` 命令类型和审计原因继续复用；
- 已经处于 `escalated` 的旧工单不自动降级；
- 已有历史审计事件保持原样。

## 10. 验收测试

自动化测试至少覆盖：

1. 第一次有效 AI 回答后，用户可立即点击转人工；
2. 用户首次输入明确“转人工”时，在存在活动工单的前提下可直接升级；
3. 页面和配置不再包含 `1/3`、`2/3`、`3/3` 或三次准入限制；
4. “设备丢了或坏了，资产还能恢复吗？”在首轮和第三轮都进入 AI 诊断；
5. “恢复后余额为零”先进入 AI 排查或澄清；
6. “交易失败了”不自动升级；
7. “发现一笔不是我发起的转账”自动升级；
8. “我已经把助记词发给陌生人”先脱敏，再自动升级；
9. 普通低风险 Triage 连续两次结构校验失败时进入 `pending_user` 澄清；
10. 已有 high/critical 风险时 Triage 失败仍进入 `escalated`；
11. 低风险回退不沿用上一轮 category、summary 或风险作为本轮判断；
12. 用户主动转人工与自动风险升级在工作台显示不同原因；
13. 原始秘密不出现在 Ticket Store、事件、checkpoint 或客户回复中；
14. `device_reset`、`bootloader_recovery` 和 `warranty_decision` 只返回安全说明和人工入口，不自动升级；
15. `unofficial_firmware`、`device_auth_failure` 和泛化远程协助咨询不因单个 flag 自动升级；
16. 全量现有状态机、会话超时、用户确认结案和人工动作测试继续通过。

浏览器验收使用同一张会话工单依次测试普通设备问题、恢复问题、模糊资金问题、明确未授权交易和用户主动转人工，并确认输入框、状态标签、工作台原因和审计轨迹一致。

## 11. 成功标准

- 用户从第一次回答开始拥有最终人工选择权；
- 普通问题不会仅因模型 Schema 输出错误自动进入人工队列；
- 物理设备丢失不再等同于资产丢失；
- 明确未授权资产移动和凭证泄露仍能自动升级；
- 所有敏感原文继续在持久化前被移除；
- 自动升级原因对用户和工作台均可解释；
- 项目仍能在面试中清楚说明“用户控制、AI 判断、确定性安全规则”三者的边界。

## 12. 已知取舍

- 取消三次门槛会增加理论上的人工请求量，但求职 Demo 没有真实坐席容量，优先保证用户控制和演示顺畅；
- 收窄自动升级可能让部分边缘风险先进入澄清，因此高风险入口信号和风险粘性必须保留；
- DeepSeek 仍可能产生语义误判，策略包和正反例只能降低概率，最终路由仍由确定性校验和 fallback 约束；
- Streamlit Demo 内的人工工作台只是流程模拟，不代表生产级客服系统。
